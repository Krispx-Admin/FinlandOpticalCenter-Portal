================================================================================
 1. WHAT THE PORTAL IS
================================================================================

A real-time operations board for a multi-branch optical retail chain in Oman.
Retail branches, lens-fitting centres, eye clinics and one central warehouse
all sign in to the same site and look at the same live data (Supabase /
Postgres + realtime).

Five modules (sidebar order):
  1. Fitting Log        — a frame's physical journey branch -> fitting centre -> branch
  2. Stock Requests     — branch asks the warehouse for stock (admin sees it as
                          "Warehouse Queue" with a warehouse icon)
  3. Lens Stock         — MGM holds the loose-lens shelf; everyone else shops it
  4. Insurance Claims   — printable A4 claim receipt (products, Rx grid, payment)
  5. Settings (admin)   — request categories, brand groups, branch sign-in codes

Plus a hidden PRESENTER MODE (?present in the URL) used to record the staff
tutorial video. See section 10.

4.2 FITTING LOG (orders)
------------------------
order.ref = the branch's own BILL NUMBER from the paper bill book (unique per
branch, not globally — index orders_ref_per_branch). Never auto-suggest it
(that was removed on purpose). Customer name is REQUIRED (trimmed).

LONG ROAD (FIT_FLOW):
  pending -> to_fitter -> at_fitter -> ready -> returning -> delivered
  status     label                 pill color  action button      who acts
  pending    Waiting for Lenses    slate       Send to fitter     origin
  to_fitter  In transit to X       blue        Confirm arrival    fitter
  at_fitter  Waiting to be Fitted  purple      Mark ready         fitter
  ready      Ready                 green       Send to branch     fitter
  returning  Returning to X        teal        Confirm delivery   origin
  delivered  Delivered             done(grey)  —                  —
  (Labels chosen by the user on 2026-10-08; they briefly made to_fitter
   "Waiting to be Fitted" too, then asked for "In transit" back.
   fitStep(o) names the place: "In transit to MGM", "Returning to SCC" — code
   in the list, full name with long:true in drawer/hover; chips use the
   generic FIT_STATUS label "In transit".)
  Filter chips are built one per DISTINCT label (fitting.js CHIP_DEFS), so if
  two stages ever share a label again they share a chip automatically.

SHORT ROAD (SELF_FLOW) — fitter === origin (a fitting centre fits its own sale):
  pending -> at_fitter -> delivered, labels Waiting for Lenses / In fitting / Done,
  actions "Start fitting" / "Mark as done". No transit, journey diagram shows
  one node + "In-house — no transit". onShortRoad(o) is only true if the
  current status is on SELF_FLOW, so legacy self-fit orders mid-long-road
  finish the long way.

Send to fitter: picker modal of FITTERS; if all selected orders came from one
fitting centre, that centre leads the list ("Keep here — no transit").
Rows are click-to-select; bulk bar advances all selected when they share the
same next action. Urgent flag (red left border, pulsing zap pill, sorted first).
Every change writes an order_events row (the human sentence shown in the
timeline AND used as the realtime toast).

4.3 STOCK REQUESTS
------------------
Statuses: placed (blue) -> completed (green). No review step.
Branch composes lines: category / brand / audience / qty / note.
Per-category rules come from Settings: needsBrand, needsAudience, needsQty,
unit ('pcs' | 'box'), brandGroup. Category/brand/audience are COPIED onto
lines so old requests stay readable after settings change.
Warehouse: Print pick sheet (new window, browser print) -> fulfil -> Complete
(RPC complete_stock_request, admin only, atomic).
Refs SR-1001… from DB sequence.

4.4 LENS STOCK
--------------
MGM keeps the shelf (rows: type, index, coating, SPH, CYL, qty; unique per
spec). Others browse a card grid, build a basket (cart, per-visit only),
"Review & request". Lens types/indices/coatings lists live in lens_catalogue
(edited by MGM or WH via the cog on the shelf tab; defaults in data.js).
A value in use on the shelf can't be removed; "None" coating can't be removed;
a list can't be emptied. LOW_LENS_STOCK = 4 (amber).

Lens request statuses: requested "Awaiting MGM" (amber) / confirmed (green) /
declined (red, with reason).

FULFILMENT (schema-07) — every lens request also OPENS A FITTING ORDER, in one
DB transaction (create_lens_request):
  send_frames  "Send the frame over"  -> order fitter = MGM, long road
  receive_lens "Receive the lenses"   -> order fitter = requester (self-fit);
                only fitting centres/admin may choose this (checked in DB)
Bill number + customer name required on the request (they become the order).

AUTO-DEDUCT (schema-08, asked for 2026-10-08): MGM no longer confirms.
create_lens_request locks each shelf row, refuses the WHOLE request if any
line is short ("Only N left of … — refresh and try again"), deducts, and
inserts the request already 'confirmed'. Line specs are copied from the shelf
row, not from the browser. One lens_request_event per request.
Legacy: confirm_lens_request + the Confirm/Decline UI remain for any request
still 'requested' (placed before schema-08). MGM's lens list now defaults to
the "All" chip.

STOCK LENS TAG: a fitting order opened by a lens request (lens_requests.order_id)
shows a "Stock Lens" tag under its journey in the list (and in the row
subtitle below 1180px), and its drawer has a "Stock lens" section: request
status, fulfilment chip, LR ref, and the lines (type, index, coating, SPH, CYL,
qty). Lookup: store.lensRequestForOrder(orderId). No DB change needed.

4.5 INSURANCE CLAIMS
--------------------
Fields: date, branch, bill no, customer (required), products (name + price,
OMR with 3 decimals — 1 rial = 1000 baisa), Rx grid, payment cash|card.
Refs IC-3001… from DB sequence. Total = sum of items (client computes;
DB trigger also maintains claims.total).
Rx grid: rows D (Distance) and N (Near); OD and OS each SPH · CYL · AXIS · V.A.;
one ADD per eye across the bottom. 9 columns, colgroup + table-layout:fixed
so SPH never gets squeezed. IPD and segment height were REMOVED on purpose
(not on insurance claims); legacy columns ipd/sh_od/sh_os are ignored.
Rx values are TEXT (opticians write PL, 6/6, N5…).
Old flat {od, os} rx shapes are folded into the D row by normaliseRx().
Preview modal and printed A4 use the SAME markup + RECEIPT_CSS (what you see
is what prints). Edit = delete+reinsert items and rx rows.

4.6 SETTINGS (admin only)
-------------------------
- Categories: drag to reorder; flag chips Brand / Audience / Quantity;
  "Counted" pcs|box; "Brands from" brand group.
- Brand groups: rename inline, drag groups, drag brands between groups
  (same brand may sit in several groups).
- Branch access: set any location's 6-digit code via RPC set_branch_code
  (rejects weak codes like 123456, 000000, <3 distinct runs). Codes cannot
  be read back by anyone. Shows last sign-in.
Settings = one JSON row (app_settings id=1), written whole, optimistic UI,
rolled back from server on refusal.

Tables (public): branches, orders, order_events, stock_requests,
stock_request_lines, stock_request_events, lens_stock, lens_requests,
lens_request_lines, lens_request_events, claims, claim_items,
claim_prescriptions, app_settings (1 row), lens_catalogue (1 row).
All have RLS on. All are in the supabase_realtime publication.

Column naming: DB uses *_code (origin_code, fitter_code, branch_code, by_code)
and lens_type / lens_index (SQL-unfriendly words). The app uses origin, fitter,
branch, type, index. ALL mapping lives in js/db.js (toOrder, toRequest, …,
orderRow, claimRow …). lens_requests.note holds the BILL NUMBER (app: billNo).

Rules followed so far:
  - Anything that must be atomic or must not trust the browser is a
    SECURITY DEFINER plpgsql function that checks the caller first
    (is_admin / is_lens_owner / jwt_branch), then does the work.
  - Refs come from sequences inside the INSERT (never client counters).
  - Single-row JSON docs (settings, lens catalogue) start EMPTY; the app
    falls back to the defaults in data.js — one definition of defaults.
  - Child rows are fetched embedded (`*, order_events(*)`), one request per
    collection.
  - Status updates are guarded: `.eq('status', from)` so a row someone else
    already moved is skipped, not double-advanced.

6.1 Module shape
  export function xxxView(me) {          // me = { code, name, role }
    const ui = { …filters, seen:Set, prevStatus:Map };
    let root, drawer = null, drawerId = null;
    …HTML builders returning template strings…
    return { mount(container){…}, onChange(event){…}, unmount(){ closeLayer(); } };
  }
  Registered in MODULES in js/app.js (label, icon, make, adminLabel?, adminOnly?).
  Screen anatomy, top to bottom:
    header.mod-head  (h1 + p.mod-sub on left, primary .btn on right)
    section.stats    (4 .stat tiles; .stat-brand / .stat-red / .stat-amber)
    section.toolbar  (.searchbox + .sel dropdowns + toggle chip)
    section.chips    (filter .chip with .chip-n count; .on = selected)
    section.list     (.row cards)
  Detail = right-side DRAWER (openLayer('drawer')); create/edit = MODAL
  (openLayer('modal')). Both start with .dw-head: .dw-kicker (small caps),
  h2, .dw-sub, and an .icon-btn [data-close] with icons.x.
  Drawer body: status row (pill + "updated 3m ago"), facts (.kv grid or
  table.lines), .dw-actions, then "Timeline" (.tl-h + .timeline, newest first,
  top dot highlighted .tl-now).

6.2 Rendering & events
  - HTML via template strings. ALWAYS esc() any user/DB text.
  - Event delegation on root / layer.el with data-* attributes
    (data-open, data-advance, data-send-fitter, data-chip, data-close, data-del…).
    [data-stop] marks regions whose clicks must not open/select the row.
  - Re-render partially (refreshLists/refreshBody) and PRESERVE FOCUS/CARET of
    the field being typed in (see lens.js refreshBody, settings.js focusKey).
  - When a modal redraws, read typed values back into a draft first (sync()).
  - New rows animate (.row-enter) by comparing to ui.seen; changed statuses
    flash (.pill-flash) by comparing to ui.prevStatus; call markSeen() after.
  - Forms that write to the DB: disable the button, show "Saving…"/"Placing…",
    keep the form open if the store returns null (refused), restore the label.
  - Trim inputs and put the trimmed value back before reportValidity() so
    whitespace-only input is rejected by the browser's own validation.

6.3 Store / data flow
  - Modules read store.state synchronously (cache).
  - Every mutation: store.run([collections], async work, describe)
      work() writes via supabase, throws on error (ok() helper), may return SKIP
      then the collections are reloaded, then commit(event) notifies views.
      Errors -> toast "That did not save" + explain(e) in plain English.
  - Event objects: { by, module, title, sub, refs:[ids], remote }.
  - Realtime: db.watch debounces bursts (220ms), reloads touched collections,
    and turns new *_events rows into toasts for OTHER branches only.
  - Add new error translations in explain() in store.js.
  - Add new tables to: SELECTS or DOCS (db.js), TABLE_COLLECTION (db.js),
    MODULE_OF (store.js), the realtime publication (SQL), RLS (SQL).

6.4 Permissions — always two layers
  RLS / definer-function checks in SQL (the real guard) + canSee*/canAdvance*
  in data.js (UI). The browser is never the only check.

6.5 Writing style (code, UI copy, commits) — match it
  - British spelling: centre, colour, catalogue, normalise, organise.
  - Comments explain WHY in full plain sentences, often a short paragraph.
    Section headers: `// ── Title ──` in JS, `-- ════` banners in SQL,
    `/* ── Title ── */` in CSS.
  - UI copy: plain, specific, sentence case, em dashes (—), curly quotes
    (“ ” ’), ellipsis character (…). Name places, not roles ("In transit to
    MGM", not "In transit to fitter"). Short helper text in .muted <p>.
  - Toast titles name the actor + ref: "SCC placed stock request SR-1004".
  - Commit messages: plain-English imperative title describing the outcome
    ("Let the shelf's keeper edit its lists; …"), body = prose explaining the
    why, "·" bullets where listing, then the Co-Authored-By trailer.
    STANDING RULE (user, 2026-10-08): commit AND push to origin/main after
    every change, including updates to this file. No need to ask first.
  - Migrations: new file supabase/schema-NN-topic.sql with a banner header,
    "STATUS: applied / NOT YET APPLIED", idempotent SQL (if not exists,
    drop … if exists, on conflict). Update this file's section 5 after.
