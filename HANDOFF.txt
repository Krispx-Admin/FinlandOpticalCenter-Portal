================================================================================
 1. WHAT THE PORTAL IS
================================================================================

A real-time operations board for a multi-branch optical retail chain in Oman.
Retail branches, lens-fitting centres, eye clinics and one central warehouse
all sign in to the same site and look at the same live data (Supabase /
Postgres + realtime).

Seven modules (sidebar order):
  1. Fitting Log        — a frame's physical journey branch -> fitting centre -> branch
  2. Stock Requests     — branch asks the office for stock (office and Ghiath see
                          it as "Office Queue" with a warehouse icon)
  3. Lens Stock         — the lens holders' shelves (MGM first). Tab shown only to
                          holders + admins; other branches order shelf lenses
                          inside New fitting order → Lens stock
  4. Reimbursement Invoice (was Insurance Claims) — printable A4 invoice (products, Rx grid, payment)
  5. Direct Insurance   — same record + insurer (OQIC/LIVA/Mednet) + salesperson;
                          office & Ghiath get a "paid by insurance" dashboard. 4.8
  6. Schedule           — the staff scheduler (scheduler.html), unchanged, inside
                          the portal; data in Postgres. See 4.7.
  7. Settings (admin)   — tabs on/off (maintenance), request categories, brand
                          groups, Direct Insurance insurers, branch sign-in codes

Plus a PUBLIC "View schedule" page (#/view-schedule, button top-right of the
sign-in screen) that needs no code: the PUBLISHED weeks that haven't finished.

Plus a hidden PRESENTER MODE (?present in the URL) used to record the staff
tutorial video. See section 10.

4.2 FITTING LOG (orders)
------------------------
order.ref = the branch's own BILL NUMBER from the paper bill book (unique per
branch, not globally — index orders_ref_per_branch). Never auto-suggest it
(that was removed on purpose). Customer name is REQUIRED (trimmed).

LONG ROAD (FIT_FLOW):
  pending -> lenses_in -> to_fitter -> at_fitter -> ready -> returning -> delivered -> collected
  status     label                 pill color  action button      who acts
  pending    Waiting for Lenses    slate       Lens received      origin
  lenses_in  Lenses Delivered      cyan        Send to fitter     origin
  to_fitter  In transit to X       blue        Frame received     fitter
  at_fitter  In Fitting            purple      Mark ready         fitter
  ready      Ready                 green       Send to branch     fitter
  returning  Returning to X        teal        Frame received     origin
  delivered  Ready for collection  green       Handed to customer origin
  collected  Collected             done(grey)  —                  —
  ('collected' added 2026-10-13, schema-31: when the glasses are back, the
   branch marks them handed to the customer. "Completed" chip = collected;
   "All active" = everything not collected; isBack(o) = delivered|collected.
   SELF and outside-cutter roads end the same way. The 37 orders that were
   'delivered' then became 'collected' with their dates kept.)
  (Labels chosen by the user on 2026-10-08; they briefly made to_fitter
   "Waiting to be Fitted" too, then asked for "In transit" back.
   fitStep(o) names the place: "In transit to MGM", "Returning to SCC" — code
   in the list, full name with long:true in drawer/hover; chips use the
   generic FIT_STATUS label "In transit".)
  lenses_in added 2026-10-11 (user): the lenses arrive at the branch first,
  then "Send to fitter" when the driver comes. The fitter PICKER now opens from
  lenses_in (needsFitter = lenses_in && !fitter; store.sendOrdersToFitter guards
  .eq('status','lenses_in')). The journey diagram looks up stages BY NAME
  (at('to_fitter') etc.), so pending and lenses_in draw identically.
  Bulk "Send to fitter": orders without a fitter go through the picker, ones a
  lens request already gave a fitter just advance.
  Filter chips are built one per DISTINCT label (fitting.js CHIP_DEFS), so if
  two stages ever share a label again they share a chip automatically.

SHORT ROAD (SELF_FLOW) — fitter === origin (a fitting centre fits its own sale):
  pending -> lenses_in -> at_fitter -> delivered, labels Waiting for Lenses /
  Lenses Delivered / In fitting / Done, actions "Lenses delivered" / "Start
  fitting" / "Mark as done" (lenses_in added here too, 2026-10-11, user). No transit, journey diagram shows
  one node + "In-house — no transit". onShortRoad(o) is only true if the
  current status is on SELF_FLOW, so legacy self-fit orders mid-long-road
  finish the long way.

OUTSIDE ROAD (OUT_FLOW) — sent to a 3rd-party cutter (added 2026-10-12, user):
  pending -> lenses_in -> to_fitter -> delivered. In "Send to fitter" the picker
  lists our centres, then "Outside — 3rd-party cutters": the names in
  app_settings.outside_cutters (office: "Outside cutters" button in the Fitting
  Log header, cuttersModal in fitting.js), or one "Outside cutter"
  (OUTSIDE_DEFAULT) when none are named. store.sendOrdersOutside sets
  orders.outside_cutter = name, status to_fitter (guard: lenses_in, fitter_code
  null, outside_cutter null); fitter_code STAYS NULL. o.outside = the name;
  isOutside(o). At the cutter: pill "At <name>" (purple), journey pins
  origin-OUT-origin, own chip "Outside" (excluded from "In transit"), admin
  fitter filter "Outside cutters". The cutter has no account, so the ORIGIN does
  every step: "Received back" -> delivered. needsAction is false while it is at
  the cutter (it waits on the cutter, not the branch).

ORDERS OPENED BY A LENS REQUEST (reworked 2026-10-12, schema-21 — no confirm).
  store.linkLensRequests() puts o.lensRequest = {id, status, fulfilment, ref,
  holder} on each order after every load/pull. The HOLDER can read these
  orders (RLS orders_lens_holder_read; canSeeOrder) so its Fitting Log shows
  them — only while the lenses are still to send (user 2026-10-13: once sent,
  where the job goes is not the holder's concern; it stays in Lens Stock). fitStep():
    send_frames: order created at lenses_in, fitter = holder ->
                 "Lenses at <holder>" + Send to fitter (origin) -> normal road.
                 The HOLDER reads it as "Waiting for frame from <origin>"
                 (fitStep(o, {viewer}) — fitting.js passes viewer: me.code).
    CHANGE HOW (schema-22): the ordering branch or the office can switch a
                 request between send-the-frame and receive-the-lenses while
                 nothing has moved (fulfilmentSwitch(): receive->send while the
                 order is pending; send->receive while it is lenses_in at the
                 holder) — button in the Stock lens section of the Fitting Log
                 drawer and in the Lens Stock request drawer; RPC
                 change_lens_fulfilment; both timelines record it.
    receive_lens, request 'requested' (pending) -> "Waiting for Lenses" from
                 the moment it is ordered (user, 2026-10-12; long form in
                 drawer/hover: "— <holder> to send them" / after: "— sent by
                 <holder>"), actor 'lens' = holder: the holder's row/drawer has
                 "Send lenses" (canSendLenses -> store.sendLenses -> RPC
                 send_lens_request); everyone else "waiting on <holder>".
                 canAdvanceOrder() is false.
    'sent' -> plain "Waiting for Lenses" + Lenses delivered (origin), then:
                 fitting centre = self-fit (fitter = itself) -> Start fitting;
                 shop/clinic (fitter null) -> Send to fitter (picker/outside).
    'declined' (pending) -> "Lens Declined" (red); the normal action stays.
  needsAction(o, code) (data.js) drives the nav badge and "Need your action":
  any advanceable order except a self-fit job still pending, PLUS lenses this
  holder has to send.

Send to fitter: picker modal of FITTERS; if all selected orders came from one
fitting centre, that centre leads the list ("Keep here — no transit").
Rows are click-to-select; bulk bar advances all selected when they share the
same next action. Urgent flag (red left border, pulsing zap pill, sorted first).
Every change writes an order_events row (the human sentence shown in the
timeline AND used as the realtime toast).

(RPC complete_stock_request, admin only, atomic).
Refs SR-1001… from DB sequence.

SEVERAL HOLDERS (schema-20, 2026-10-12): any open fitting centre the office

lens_stock row and lens_requests row has holder_code (all old data = MGM).
Rows: holder, type, index, coating, SPH, CYL, qty; unique per holder+spec.
A holder: tabs Incoming requests (made TO it) · My shelf (edit counts, add,
remove) · and, if other holders exist, Other shelves (shop) · My requests.
A non-holder: Browse lenses · My requests, with a "Shelf at …" picker when

per-visit only), "Review & request". Lens types/indices/coatings lists live in
lens_catalogue — SHARED by all holders (edited by any holder or the office via
the cog on the shelf tab; defaults in data.js).
A value in use on the shelf can't be removed; "None" coating can't be removed;
a list can't be emptied. LOW_LENS_STOCK = 4 (amber).

Lens request statuses (schema-21): reserved "Set aside" (send the frame) /
requested "Lenses to send" (receive, not yet sent) / sent / declined (with
reason) / confirmed (older requests only).

FULFILMENT — every lens request also OPENS A FITTING ORDER, in one DB
transaction (create_lens_request). EVERY branch chooses (user, 2026-10-12);
the default is send_frames:
  send_frames  "Send the frame"      -> order fitter = holder, status lenses_in
  receive_lens "Receive the lenses"  -> order pending, fitter NONE (schema-29;
                                        was self-fit for fitting centres). After
                                        Lenses delivered the branch uses Send to
                                        fitter: Keep here (open bench) or any
                                        open fitter / outside cutter.
  A holder whose bench is closed cannot be sent the frame (create and change
  refuse; the cart greys "Send the frame").
Bill number + customer name required on the request (they become the order).

back, schema-21 reserve-on-order + send (user chose these three decisions).

STOCK LENS NOTE: a fitting order opened by a lens request (lens_requests.order_id)
shows "Stock Lens" under its journey in the list (and in the row

4.9 OUTSIDE LENS ORDERS (TRIAL — the user may drop it; reworked 2026-10-13, schema-30)

NEW ORDER: "Outside lenses · other brands" switch (fields only when on):
R/L × SPH/CYL/AXIS/ADD, typed lens type, and the way:
  · SEND THE FRAME TO A FITTER — a select of OPEN fitting centres (not the
    branch itself; default MGM) — the frame goes from the branch AND the
    lenses go from AV, two legs to that one fitter (dest).
  · RECEIVE THE LENSES HERE — AV sends the lenses to the branch.
  Default: a branch with its own open bench → receive; others → send.
  The handler's own orders: no choice; the lenses arrive at AV.
  RPC create_outside_lens_order(bill, customer, rx, lens_type, fulfilment, dest).

received_at.

FLOW / WHO DOES WHAT
  AV (Outside tab + Fitting Log) — for AV the lens follows the normal steps
  (schema-32, 2026-10-14), and its Fitting Log chips follow the LENS, not
  the frame (handlerStage):
    Waiting for Lenses: "Order lens" (amber, opens the tab) → Confirm order →
      "Lenses ordered" (green) + "Lens received" when they reach AV (RPC
      outside_lenses_arrived, arrived_at)
    Lenses Delivered: "Send lenses to <dest>" (refused before arrival)
    In transit: "In transit to <dest>", waiting on <dest>
    → leaves AV's log once the dest receives them. These rows can't be
      bulk-selected by AV. Undo (un-order) is refused once arrived.
  SEND THE FRAME: order fitter = dest, status lenses_in. Branch: "Lenses
    being ordered" / "Lenses ordered at AV" / "Lenses on the way to MGM" /
    "Lenses at MGM" + "Send frame to MGM" (any time). Fitter: "Waiting for
    frame from X"; "Lenses received" button once AV sent them (RPC
    receive_outside_lenses); with the frame there but no lenses: "Lenses on

    them, "Lenses delivered" (that also records received_at); then Send to
    fitter — Keep here / any open fitter / outside cutter.
  AV's own: pending; "Order lens" → "Lenses ordered" → Lenses delivered.
  CHANGE: the branch (or office) can switch the way or the fitter while
    nothing has moved (drawer "Change" → same choices; RPC

6.2 Rendering & events
  - HTML via template strings. ALWAYS esc() any user/DB text.
  - Event delegation on root / layer.el with data-* attributes
    (data-open, data-advance, data-send-fitter, data-chip, data-close, data-del…).
    [data-stop] marks regions whose clicks must not open/select the row.
  - Re-render partially (refreshLists/refreshBody) and PRESERVE FOCUS/CARET of
    the field being typed in (see lens.js refreshBody, settings.js focusKey).
  - When a modal redraws, read typed values back into a draft first (sync()).
  - New rows animate (.row-enter) by comparing to ui.seen; changed statuses
    flash (.pill-flash) by comparing to ui.prevStatus; call markSeen() after.
  - Forms that write to the DB: disable the button, show "Saving…"/"Placing…",
    keep the form open if the store returns null (refused), restore the label.
  - Trim inputs and put the trimmed value back before reportValidity() so
    whitespace-only input is rejected by the browser's own validation.

6.3 Store / data flow
  - Modules read store.state synchronously (cache).
  - Every mutation: store.run([collections], async work, describe)
      work() writes via supabase, throws on error (ok() helper), may return SKIP
      then the collections are reloaded, then commit(event) notifies views.
      Errors -> toast "That did not save" + explain(e) in plain English.
  - Event objects: { by, module, title, sub, refs:[ids], remote }.
  - Realtime: db.watch debounces bursts (220ms), reloads touched collections,
    and turns new *_events rows into toasts for OTHER branches only.
  - Add new error translations in explain() in store.js.
  - Add new tables to: SELECTS or DOCS (db.js), TABLE_COLLECTION (db.js),
    MODULE_OF (store.js), the realtime publication (SQL), RLS (SQL).

6.4 Permissions — always two layers
  RLS / definer-function checks in SQL (the real guard) + canSee*/canAdvance*
  in data.js (UI). The browser is never the only check.

6.5 Writing style (code, UI copy, commits) — match it
  - British spelling: centre, colour, catalogue, normalise, organise.
  - Comments explain WHY in full plain sentences, often a short paragraph.
    Section headers: `// ── Title ──` in JS, `-- ════` banners in SQL,
